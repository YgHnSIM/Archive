그래프 엔지니어링: 카파시의 루프에서 앤트로픽의 지식 그래프까지

카파시는 GPU 한 대에서 도는 자동 실험 루프(autoresearch)를 만들었고, 에이전트 여럿이 커밋 그래프로 협업하는 AgentHub를 스케치했다. 앤트로픽은 다섯 가지 워크플로 패턴, 최대 1,000개 하위 에이전트를 띄우는 Dynamic Workflows, 지식 그래프 구축 쿡북을 내놓았다. 이 노트는 두 흐름을 하나로 엮어 "루프에서 그래프로" 가는 단계별 구축 경로를 제시한다.

1서론: 병목마다 바깥으로 꺼내는 구조

카파시의 autoresearch README는 일부러 과장한 미래사로 시작한다. "예전엔 사람이 먹고 자고 '그룹 미팅'으로 동기화하며 AI 연구를 했다. 이제 연구는 전적으로 AI 에이전트 무리의 영역이다."

2025년 초 바이브 코딩은 낮은 바닥선을 그었다. 2026년에는 에이전틱 엔지니어링이 더 높은 직업적 기준을 세웠다. 사람은 보안, 정확성, 아키텍처, 안목, 검증에 계속 책임진다.

autoresearch는 이 전환을 머신러닝 실험으로 밀어 넣는다. GPU 한 대짜리 작은 학습 환경을 주고 에이전트에게 한 번에 하나씩 바꾸게 한다. 핵심 코드는 약 630줄이고, 긴 실행에서 이틀 동안 실험 약 700회를 돌려 쓸모 있는 최적화 약 20개를 남겼다고 한다.

다음 단계는 협업이다. 카파시는 autoresearch가 SETI@home처럼 "에이전트들이 비동기로, 대규모로 협업"해야 하며 목표는 박사과정생 한 명이 아니라 연구 공동체를 흉내 내는 것이라고 썼다(2026년 3월 8일 게시물). AgentHub가 그 층의 스케치다.

아키텍처마다 바깥으로 꺼내는 병목

  • 루프: 반복과 평가
  • 체인: 작업 순서
  • 스웜(무리): 병렬 탐색과 역할 분담
  • DAG: 실험의 계보
  • 지식 그래프: 공유 사실, 출처, 세션을 넘는 기억

이 노트의 독자는 LLM 호출은 할 줄 알고, 그 주변에 시스템을 얼마나 쌓을지 정해야 하는 엔지니어다. 파이썬, Git, JSON 스키마, 기초 그래프 용어를 안다고 가정한다.

2카파시의 루프: autoresearch

에이전트를 실행 가능한 연구 틀(하네스) 안에 넣는다. 하네스는 고칠 수 있는 학습 프로그램, 고정된 평가 지표, 시간 예산, Git 기록, 지시문을 제공한다. 중심 파일은 세 개다.

  1. prepare.py: 데이터 준비와 평가 도구. 에이전트가 고치지 않는다.
  2. train.py: 모델, 최적화기, 하이퍼파라미터, 학습 루프. 에이전트가 고치는 실험면이다.
  3. program.md: 연구 절차, 제약, 지표, 기록 규칙, 자율 정책을 적은 문서.

무한 반복 절차

  1. 현재 train.py와 최근 기록을 읽는다.
  2. 근거 있는 변경 하나를 제안한다.
  3. 후보 변경을 커밋한다.
  4. 약 5분간 학습한다.
  5. val_bpb와 최대 메모리를 잰다.
  6. 충돌하면 살펴보고, 기계적 문제면 고치고 아니면 되돌린다.
  7. val_bpb가 좋아지면 커밋을 남기고, 아니면 직전에 남긴 커밋으로 되돌린다.
  8. 결과를 기록하고 사람에게 묻지 않고 계속한다.

프로그램을 프로그래밍하기

소프트웨어 1.0은 명시적 명령을, 2.0은 데이터와 학습을, 3.0은 맥락과 프롬프트를 프로그래밍한다고 카파시는 말한다. autoresearch는 한 층을 더 얹는다. 자연어 지시문이 자율 조직 하나를 설정한다. 좋은 program.md에는 고칠 파일과 보호할 파일, 지표와 개선 방향, 실험 예산, 실행 명령, 출력 해석, 충돌 처리, 커밋·되돌리기 규칙, 기록, 사람에게 넘길 기준, 종료 조건이 들어간다.

보고된 결과와 그 의미

이틀간 실험 약 700회, 남긴 최적화 약 20개다. QK 정규화 스케일, 값 임베딩 정규화, AdamW 설정 조정이 포함된다. 밤새 돌린 보고서에는 배치 크기, 깊이, 임베딩 학습률, RoPE 기준 주파수, 가중치 감쇠, 초기화 크기, 학습률 감소 구간 설정에서 누적 개선이 나왔다.

개별 최적화보다 구조의 교훈이 더 믿을 만하다. 사람 연구자가 머릿속에 담던 가설, 실패, 변수 간 상호작용을 기계가 읽는 기록으로 바꾼다. 모든 실험에 부모 상태, 코드 차이, 지표, 남김·버림 결정이 붙는다.

저장소는 GitHub 별 86,000개 이상, 포크 12,500개를 모았다. 인기는 과학적 성능 지표가 아니다. 코드가 작고 지표가 보이며 루프가 읽기 쉬워서 따라 하기 쉽다는 증거 정도로 보는 게 맞다.

루프가 잘 되는 네 조건

  1. 결과를 검증할 수 있다. 학습이 측정 가능한 검증 결과를 낸다.
  2. 되돌릴 수 있다. git reset으로 마지막으로 남긴 상태로 돌아간다.
  3. 주기가 짧다. 5분짜리 실행이 잦은 피드백을 만든다.
  4. 환경이 닫혀 있다. 저장소가 행동 범위를 좁힌다.

이 넷이 재사용 가능한 틀, 곧 래칫 루프가 된다. 카파시는 모델의 재귀적 자기 개선을 "최종 보스전"이라 부르며 최전선 연구소들이 이를 추구할 것이라고 했다.

3루프에서 스웜으로: AgentHub

AgentHub는 스스로를 에이전트 우선 협업 플랫폼이라 소개한다. 구호는 "GitHub는 사람용, AgentHub는 에이전트용"이다. 수천 에이전트가 동시에 탐색하고, 대부분의 결과는 병합되지 않으며, 실패한 실험도 증거가 된다. 핵심 동작은 "main에 병합"이 아니라 "탐색 그래프 순회"다. 그래서 필수 main 브랜치, 풀 리퀘스트, 병합 대기열, 정답 잎 하나라는 가정을 모두 뺐다.

구현은 작다. Go 서버 바이너리 하나, SQLite DB 하나, 디스크의 bare Git 저장소 하나, 에이전트별 API 키, 요청 횟수·번들 크기 제한, 얇은 ah 명령줄 도구다. 메커니즘과 문화를 일부러 나눴다. 무엇을 최적화할지는 프롬프트와 프로젝트 지시문이 정한다.

명령뜻
ah push현재 커밋을 허브로 올림
ah fetch아무 커밋이나 가져옴
ah children이 결과 위에서 무엇을 시도했나
ah leaves자식 없는 끝, 곧 아직 안 가 본 탐색 전선
ah lineage뿌리까지의 조상 경로
ah diff두 커밋 비교

DAG가 곧 그래프다

커밋이 노드, 부모 연결이 방향 있는 선이다. 실험 커밋에는 부모, 만든 에이전트, 가설, 코드 차이, 지표, 실행 시간, 메모리, 환경, 남김 여부, 토론 글 링크를 붙일 수 있다. 그러면 "메모리 한도 안에서 가장 좋은 결과는?", "배치 크기 변경의 후손 실험은?", "같은 최적화를 따로 재발견한 에이전트는?" 같은 질문에 답할 수 있다.

메시지 게시판은 사회적 층이다. 버려진 변경도 "이 조건에선 안 된다"는 교훈을 남긴다. 에이전트는 모든 이전 대화 기록 없이, 관련 계보와 요약 몇 개만 읽고 이어 간다. 이것이 그래프 기반 맥락 구성의 시작이다.

저장소는 "진행 중. 스케치일 뿐"이라고 경고한다. 분산 저장, 저장소 압축, 에이전트 간 신뢰, 악성 번들, 재현성, 의미상 중복 탐지, 계산 자원 배분, 장기 색인이 빠져 있다.

4앤트로픽의 인프라: 다섯 패턴에서 1,000 에이전트로

2024년 12월 가이드 「Building Effective Agents」는 가장 단순하고 조합 가능한 패턴부터 쓰라고 권한다.

프롬프트 체이닝
한 호출의 결과가 다음 호출의 입력. 순서 고정.
라우팅
분류기가 입력을 전문 프롬프트·모델·도구로 보냄.
병렬화
독립 호출을 동시에. 나눠 맡기 또는 투표.
오케스트레이터-워커
중앙 모델이 쪼개고 맡기고 합침.
평가자-최적화자
한쪽이 만들고 다른 쪽이 기준으로 평가하며 반복.

Dynamic Workflows (2026년 5월)

개발자가 정적 스크립트를 쓰는 대신 Claude가 그 작업용 자바스크립트 조율 프로그램을 쓴다. 원문 예시는 모든 .ts 파일을 감사 에이전트에게 나눠 맡기고, 신뢰도 0.70 이상인 결과만 반박 검토자에게 넘긴 뒤, 종합 에이전트가 출처 달린 보고서 하나로 묶는다.

사양: 동시 하위 에이전트 최대 16개, 워크플로당 최대 1,000개, 하위 에이전트마다 새 맥락, 중간 상태는 스크립트 변수에 둔다. "workflow"라는 단어나 ultracode 모드로 켠다. 사례로 Bun 런타임을 Zig에서 Rust로 약 75만 줄 옮기는 데 11일, 테스트 통과율 99.8%를 든다.

지식 그래프 구축 쿡북

고전적 NLP 파이프라인을 모델 호출과 구조화 스키마로 바꾼다.

  1. 추출(Haiku): 스키마로 묶은 호출이 유형 있는 개체와 S-P-O 관계를 뽑는다.
  2. 해소(Sonnet): 후보를 유형과 맥락으로 묶는다. "Edwin Aldrin"을 "Buzz Aldrin"으로.
  3. 조립: NetworkX MultiDiGraph. 노드엔 유형·출처·횟수, 선엔 술어와 출처.
  4. 질의(Sonnet): 부분 그래프를 삼항 목록으로 풀어 주고, Claude가 선 단위 인용을 달아 추론한다.

Pydantic 스키마가 유일한 "학습 데이터"다. 학습시킨 개체명 인식기와 관계 분류기가 문서당 구조화 출력 프롬프트 하나로 줄어든다.

개체 해소는 추론 작업이다. 약어, 별명, 옛 이름, 철자 변형이 섞이고, 단순 문자열 유사도로는 놓치거나 동명이인을 잘못 합친다. 쿡북은 설명문을 맥락 증거로 쓰고, 유형별로 묶은 뒤 더 강한 모델에게 대표 묶음을 제안하게 한다. 규모가 크면 값싼 신호로 후보를 먼저 줄인다. 합친 결과에는 별명, 출처 문서, 근거, 신뢰도, 실행 기록을 남겨 잘못 합친 것을 되돌릴 수 있게 한다.

여러 단계 질의(멀티홉)에 그래프 전체를 넣지 않는다. 시작 개체를 찾고, 정해진 범위만 순회하고, 유형·날짜로 걸러 직렬화한다.

2024년 가이드는 "엔지니어가 단순한 워크플로를 만든다", 2026년 기능은 "Claude가 즉석에서 워크플로를 만든다"이다. 추상화 경계는 바뀌어도 책임은 남는다. 사람은 목표, 범위 파일, 출력 계약, 권한, 검증 정책, 동시성과 토큰 예산, 되돌리기 규칙, 종합에 필요한 증거를 정한다.

5공유 기억으로서의 그래프

그래프의 세 역할

  • 공유 기억: 워커가 발견을 구조화된 그래프 갱신으로 쓴다. 스키마·출처 검증을 거쳐 트랜잭션으로 넣는다. 종합 에이전트는 원문을 다 보지 않아도 그래프를 순회해 합친다.
  • 근거 층: 평가자가 주장을 근거와 대조한다. "X사가 사고 Y의 부품을 공급했다"는 주장에 (X, 공급함, 부품Z)와 (부품Z, 관련됨, 사고Y) 선이 없으면 "수정 필요, 지지 경로 없음, 필요한 증거 두 가지"를 구조화해 돌려준다. 자유 서술 비평보다 실행하기 쉽다.
  • 지속되는 세계 모델: "에이전트는 잊어도 그래프는 잊지 않는다." 긴 조사, 세션을 넘는 계획, 모순 추적, 시점 있는 사실, 감사 기록, 모델 간 인계, 실패 후 복구가 가능해진다.

커밋 DAG와 지식 그래프는 서로 보완하며 합치면 안 된다. DAG는 "무엇이 바뀌었나, 부모 실험은, 누가 만들었나"에 답하고, 지식 그래프는 "어떤 개체가 있고 어떻게 관계되며 어떤 출처가 받치고 어떤 주장이 충돌하나"에 답한다. 실서비스는 둘을 잇는다. 예: 실행 183이 주장 441을 만들고, 그 주장은 README가 지지하며 옛 주장 238을 대체한다.

그래프가 새로운 "맥락 쏟아붓기"가 되어선 안 된다. 워커별 맥락 구성 7단계: 과제 속 개체 해소, 허용된 선으로 1~2홉 확장, 최신 산출물 버전 포함, 최근 검증 주장 우선, 충돌·불확실성 포함, 토큰 예산 안에서 직렬화, 인용용 고정 선 ID 부착.

6실전 구축 경로: 루프에서 그래프로

단계시점난도졸업 기준
반성 루프1일차낮음품질 개선이 측정됨
도구 사용2일차낮음알려진 오류 유형이 줄어듦
계획1주차중간경로가 바뀌는 과제도 완수
멀티 에이전트2주차중간역할 분담이 단일 에이전트보다 나음
지속 그래프1개월차높음세션을 넘는 질의가 작동
스웜 워크플로2개월차높음품질 손실 없이 소요 시간 단축
  1. 1일차: 평가 가능한 LLM 호출 하나에 초안 저장, 명시 기준 평가자, 수정 단계, 중단 규칙(예: 최대 3회)을 붙인다. 모든 산출물을 남긴다.
  2. 2일차: 측정된 실패 하나를 고치는 도구 하나만 추가한다. 도구마다 유형 있는 스키마, 권한, 결과 확인이 필요하다.
  3. 1주차: 경로가 바뀔 때만 계획을 쓴다. 실행 전 JSON 계획(단계, 의존, 성공 기준)을 요구하고, 의존을 먼저 검증하고, 재계획 때 성공한 작업은 보존하고, 재시도와 총비용에 상한을 둔다.
  4. 2주차: 생성자와 비평자부터. 계획, 구현, 테스트 작성, 리뷰, 보안 리뷰, 종합 역할. 인계는 모두 산출물 계약이고, 리뷰는 "좋아 보임"이 아니라 기준별 결함을 돌려준다. 같은 저장소를 여럿이 고치면 worktree로 격리한다.
  5. 1개월차: 버전 붙은 JSON이나 관계형 표로 시작한다. 개체, 주장, 출처, 관계, 산출물, 실행, 평가, 별명, 미해결 질문을 저장하고 모든 선에 출처를 단다.
  6. 2개월차: 쉽게 쪼개지는 작업 하나를 고른다(파일 전수 감사, 문서 수천 건 추출 등). 펼치기 전에 결과를 모을 리듀서를 정의하고, 동시성·총 워커·토큰·시간 제한, 재시도, 증거 계약, 중복 제거, 최종 평가 관문을 정한다.

참조 아키텍처: 다섯 평면

  • 제어: 목표 수신, 계획, 예산, 시작·중단 결정
  • 실행: 도구, 테스트, 학습, 하위 에이전트를 격리 환경에서
  • 산출물: 계획·초안·코드·보고·지표를 바뀌지 않는 버전으로
  • 그래프: 개체, 주장, 관계, 출처, 실험 계보, 작업 의존
  • 평가: 결정적 검사, 모델 평가자, 통계 채점, 사람 검토

이렇게 나누면 채팅 기록 하나가 DB, 워크플로 엔진, 감사 로그를 겸하는 일을 막는다.

7평가와 품질

평가 틀도 autoresearch와 같은 모양이다. 추출 프롬프트와 점수 기록을 읽고, 프롬프트나 스키마 변경 하나를 제안하고, 정답 세트로 추출하고, 정밀도·재현율·F1·비용·지연을 재고, 좋아지면 남기고 나빠지면 되돌린다. 원문은 이를 "그래프 autoresearch"라 부른다. 최적화 대상이 train.py가 아니라 추출 프롬프트, 온톨로지, 해소 정책, 질의 직렬화기다.

해소 지표로는 압축률, 쌍별 정밀도·재현율, 잘못 합침 비율, 놓친 합침 비율, 수동 검토 비율을 본다. 압축률이 높다고 좋은 게 아니다. 과하게 합치면 연결은 됐지만 틀린 그래프가 된다.

층지표흔한 오독
추출개체·관계 F1높은 정밀도가 빠진 개체를 가림
해소쌍별 정밀도·재현율압축만 보면 과잉 병합을 보상
그래프연결 요소, 밀도요소 하나가 늘 바람직하진 않음
질의정확도, 인용 경로매끄러운 답이 엉뚱한 선을 인용
워크플로과제 성공, 비용에이전트를 늘리면 가치 없이 활동만 증가
운영복구, 수정평균 성공률이 치명적 사례를 가림

멀티홉 답은 답과 경로를 함께 평가한다. 개체를 바로 해소하고, 관련 부분 그래프를 가져오고, 지지된 선만 쓰고, 시간·출처 제약을 지키고, 사실과 추론을 구분하고, 쓴 선을 인용하고, 빠진 증거를 밝혀야 한다. 헷갈리는 별명, 서로 다른 날짜, 끊긴 경로로 적대적 사례를 만든다. 운영에선 단일 점수보다 추세를 본다. 고립 노드가 갑자기 늘면 해소 퇴행, 갑자기 줄면 과잉 병합 신호일 수 있다.

8결정 틀

고르기 전 여섯 질문

  1. 성공을 검증할 수 있나? 아니면 자율로 시작하지 말고 테스트·채점표·사람 결정부터 정한다.
  2. 단계가 안정적인가? 그렇다면 체인, 아니면 계획이나 오케스트레이터.
  3. 하위 작업이 독립적인가? 그렇다면 병렬화, 아니면 의존을 명시하고 동시 쓰기를 제한.
  4. 대안 계보를 살려 둬야 하나? 그렇다면 브랜치 하나 대신 DAG.
  5. 사실이 실행 뒤에도 남아야 하나? 그렇다면 산출물과 그래프 상태를 저장. 대화 요약에 기대지 않는다.
  6. 비용과 지연을 감당할 수 있나? 워커를 늘리기 전에 예산부터.

실행마다 복잡도 예산을 선언한다. 모델 호출, 하위 에이전트, 동시 워커, 도구 호출, 소요 시간, 토큰, 금액, 재시도, 그래프 쓰기의 최대치와 마무리에 필요한 최소 증거다. 예산이 바닥나면 현재 최선의 산출물, 끝낸 일, 남은 문제, 멈춘 이유를 돌려준다. 부분 실패를 매끄러운 답 뒤에 숨기지 않는다.

에이전트가 있다는 이유만으로 지식 그래프를 넣지 않는다. 작업이 독립적이거나, 세션 간 상태가 필요 없거나, 문서 하나로 답이 되거나, 관계가 단순하고 고정됐거나, 관계형 표로 다 되거나, 출처가 필요 없거나, 추출 오류가 순회 가치보다 크면 불필요하다.

9한계

  • autoresearch는 최전선 연구가 아니다. 저장소와 지표가 닫혀 있어 된다. GPU 한 대에서 되는 루프가 실서비스 학습 플랫폼의 안전한 자기 수정을 증명하진 않는다. 옮길 것은 구조다.
  • 지표는 속을 수 있다. 래칫은 보이는 지표만 올린다. 검증 손실이 줄어도 추론 비용 증가, 견고성 저하, 평가셋 과적합이 생길 수 있다.
  • AgentHub는 실서비스 소프트웨어가 아니다. 인증, 격리, 저장 내구성, 색인, 재현성, 거버넌스가 더 필요하고 DAG는 가지치기·보관이 필요하다.
  • Dynamic Workflows는 비싸다. 고강도 하위 에이전트 1,000개 실행이 수십 달러가 들 수 있다. 병렬 워커는 같은 오류를 함께 낼 수 있어, 검토자는 다른 프롬프트·증거·역할을 가져야 의미가 있다.
  • 쪼개면 품질이 떨어질 수 있다. 아키텍처 설계, 서사 글쓰기, 긴밀한 리팩터링, 미묘한 제품 결정은 하나의 맥락이 필요하다.
  • 그래프는 말뭉치를 닮는다. 치우친 자료는 치우친 그래프를 만든다. 그래프는 주장을 검사 가능하게 보존할 뿐, 진실로 바꾸지 않는다.
  • 개체 해소 오류는 치명적이다. 두 사람을 한 노드로 합치면 이후 모든 질의가 둘의 직장·날짜·행동을 섞는다.
  • 그래프는 만든 사람의 판단을 증폭한다. 잘못된 목표나 세계 표현은 자동화로 규모만 커진다. 명세, 품질 기준, 수정 장치는 사람이 맡아야 한다.

10결론

흐름은 세 단계로 요약된다. 바이브 코딩(사람은 의도, 모델은 작성), 에이전틱 엔지니어링(사람이 명세·조율·검증과 품질 책임), 그래프 엔지니어링(에이전트가 유형 있고 질의 가능한 작업·지식 그래프로 지속 상태를 공유).

가장 중요한 통찰은 병목이 다음 모델 호출이 아니라 기억과 평가를 어디에 두느냐라는 점이다. 커밋 DAG는 어느 작업이 어느 실험에서 나왔는지, 지식 그래프는 어떤 주장이 어떤 개체·출처와 이어지는지 기억한다. 둘이 있으면 에이전트가 맥락 창마다 세계를 처음부터 다시 짓지 않아도 된다.

권고는 점진적이다. 측정되는 루프 하나, 되돌릴 수 있는 실패, 오류 유형 하나에 도구 하나, 경로가 바뀔 때만 계획, 전문화가 이득일 때만 역할 분리, 대화보다 산출물 먼저 저장, 대안이 살아야 할 때 DAG, 관계와 지속이 중요할 때 지식 그래프, 작업이 병렬이고 리듀서가 정해졌을 때만 스웜. 각 단계는 앞 단계의 한계를 메운다. 필수 순서는 아니지만 방향은 있다.

원문이 내세우는 기준 문장

중요한 산출물은 모두 목표, 계획, 산출물, 출처, 그래프 경로, 평가자 결정, 한도가 정해진 실행 기록까지 거슬러 추적할 수 있어야 한다.

이 문장이 거짓이면 에이전트를 늘릴수록 불투명해진다. 참이면 루프, 스웜, DAG, 지식 그래프가 조합 가능한 공학 장치가 된다. 루프에서 그래프로 가는 길은 단순함에서 복잡함으로가 아니라, 암묵 상태에서 명시 상태로, 휘발 기억에서 지속 기억으로, 추정에서 증거로 가는 길이다.

  • Dynamic Workflows(동시 16개, 상한 1,000개, ultracode 모드, 수십 달러 비용)와 Bun 75만 줄·11일·99.8% 사례는 출처에 URL이 없어 이 문서만으로 확인할 수 없다.
  • 그림 1은 "지식 그래프 스키마"라 하지만 상자 안 글이 "Title: Description" 같은 자리표시자라 본문의 노드 유형(Entity, Claim 등)과 맞지 않는다.
  • "You spin up a swarm of agents…" 카파시 인용에는 출처 번호가 없다. 참고문헌 [8], [11]은 본문에서 인용되지 않는다.
  • "앤트로픽과 무관하며 보증받지 않음"이라고 밝히면서 첫 쪽에 앤트로픽 로고가 있다.
