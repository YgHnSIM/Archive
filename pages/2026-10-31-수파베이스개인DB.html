에이전트가 원하는 것

수요 주체의 대전환

YC의 오랜 격언은 "사람들이 원하는 것을 만들어라"다. 이제 제품을 만드는 이들은 "에이전트가 원하는 것을 만들어라"라는 현실을 마주한다. Supabase는 Claude Code나 Codex 같은 도구 안에서 사실상 기본 데이터베이스가 되었고, 신규 활동의 약 70%가 에이전트에서 나온다.

그림으로 보기: 1년 사이의 변화

성장의 동력은 둘이다. 기존 소프트웨어 엔지니어들이 에이전트로 만들고 있다는 점 확인 필요 그리고 소프트웨어 배경이 없던 비엔지니어 빌더가 대거 들어왔다는 점이다.

  • 누적 가입자. 약 300만 명에서 1,300만 명.
  • 관리 DB. 800만 개에서 5,000만 개에 근접.
  • 사내 AI 코딩. 코드의 80%를 AI로 쓰는 엔지니어 10%에서 60%.
  • ChatGPT 주간 사용자. 12억 명, 잠재적 DB 생성 풀.
  • AWS 매출 중 스타트업 기여. 약 40%. 확인 필요

개발자 도구는 원래 사람의 시각적 편의를 위해 발전했다. 에이전트는 버튼보다 CLI 명령, API 호출, 텍스트 설정 파일을 훨씬 잘 다룬다. 기계가 파싱하고 조작하기 쉬운 명시적 프로토콜이 경쟁력이 된다.

2

세 시대와 오픈소스

대시보드 → API → 코드 우선

그림으로 보기: Supabase의 세 장

대시보드 시대. 개발자조차 관계형 데이터베이스를 어려워한다는 관찰에서 출발해, Postgres 위에 Airtable 같은 UI를 얹었다. 이 제품은 YC 기간 100일 만에 만들어졌다. 확인 필요

API 시대. 2021년 무렵 DB를 많이 띄워야 하는 고객이 API를 요청했다. 이 API 덕분에 2024년 Bolt와 Lovable 같은 AI 생성 도구가 쏟아질 때 Supabase가 곧바로 기본 백엔드가 되었다.

코드 우선 시대. 코플스톤은 "코드 우선, Git 네이티브" 제품 메모를 보냈다. 대시보드는 코드와 보조를 맞춰 동작해야 하고, CLI는 샌드박스 안에서 코드로 동작하도록 다시 설계했다. 또 하나는 LLM 안에서 기본 선택지로 뽑히는 것이다.

  • 전환의 계기. 대시보드는 YC 기간 100일 만의 런칭 확인 필요 API는 대규모 DB 자동 프로비저닝 고객의 피드백, 코드 우선은 에이전트가 대시보드에 오지 않고 CLI를 선호한다는 확인이었다.

오픈소스의 효과는 "반사실을 증명할 수 없지만 결정적이었다". Supabase는 PostgREST 같은 Postgres 생태계 도구의 유지보수에도 참여한다.

에이전트는 무언가 잘못되면 소스를 직접 볼 수 있기 때문에 오픈소스를 좋아하는 것 같다.

보안이 중요해질수록 기업은 소스 코드를 검사하려 하고, 닫힌 공급사는 꺼릴 것이다. Supabase는 Parse(2013년 Facebook 인수)와 Firebase(2014년 Google 인수)가 닦은 BaaS의 길, 그리고 Atlas(MongoDB)가 증명한 클라우드 3사 밖의 DB 사업 위에 서 있다.

빌더의 부상

억눌린 아이디어의 해방

빌더는 공학 훈련 없이 AI 코딩 도구로 작동하는 제품을 만드는 사람이다. 보통 가입이 급증하면 숙련도가 낮아져 활성화와 전환율이 떨어진다. 올해 Supabase에서는 "좀 미친" 일이 일어났다.

그림으로 보기: 퍼널의 역설

빌더들은 엔지니어를 설득하지 못해 오래 품어 온 아이디어를 이제 혼자 쏟아낸다. PLG는 일정 매출에서 천장에 부딪힌다는 경고가 있었지만 코플스톤은 "지금까지 천장이 없어 보인다"고 말한다. 코딩 못 하던 사람이 빌더가 되면 시장 규모 자체가 커진다.

10억 달러 이상에 엑싯한 한 핀테크 창업자는 루비 스크립트 정도만 다뤘지만, 코딩 에이전트로 은행 연동과 대차대조표 추적을 갖춘 개인 재무 소프트웨어를 혼자 만들었다. 2년 전이라면 만들어지지 않았을 소프트웨어다.

그림으로 보기: 병목의 이동

컨퍼런스에서 만난 브라질의 택시 기사는 휴대폰으로 지역용 '미니 우버' 앱 전체를 만들었다. 나이는 50세쯤으로 보였다. 확인 필요 코플스톤은 그가 10대 같은 에너지를 가졌다고 회고하며, 블루칼라 노동자였던 사람들이 이 기회를 발견하고 있다고 말한다.

개인 소프트웨어

단 한 사람을 위한 앱

이제 N=1, 단 한 사람만을 위한 소프트웨어가 현실이 된다. 진행자 하자 태거 확인 필요 는 개인 앱 '컨트롤 타워'를 만들었다. 6개월 전 OpenClaw에 빠졌을 때는 "UI는 없어지고 모든 것이 채팅이 된다"며 마크다운만 썼지만, 결국 데이터베이스와 UI가 필요해지는 지점이 왔다.

  • 수신함 분류. 에이전트가 이메일의 중요도를 판단해 처리한다.
  • 재무. Mint나 Monarch와 대등하거나 낫다. 모호한 거래의 이름을 Gbrain에서 찾아 누구인지 알아내고 분류한다.
  • 건강. 체중과 운동을 추적한다. 체중이 늘어도 캘린더를 본 에이전트가 "여행 중이었으니 괜찮다"고 말해 준다.
  • 파일. 어떤 파일이든 던지면 에이전트가 삶과 어떻게 관련되는지 판단해 Supabase에 저장한다.

코플스톤은 재무와 건강을 사람들이 자기 데이터를 갖고 싶어 하는 대표 영역으로 꼽는다. 모든 기기를 하나의 DB로 동기화하면 프롬프트로 데이터 사이의 상관관계를 뽑을 수 있다. 한 참석자는 S3 호환 Supabase 저장소에 자료를 모두 두고 있고 그것이 Gbrain의 기본값이라고 덧붙였다. 확인 필요

모든 사람의 데이터베이스

데이터 주권과 교체 가능한 에이전트

개인 에이전트를 쓸수록 루틴과 CRM이 한 에이전트 안에 갇히는 불안이 생긴다. 더 나은 에이전트가 나와도 갈아타기 어렵다. 그래서 데이터를 에이전트 밖의 독립 데이터베이스로 옮긴다.

그림으로 보기: 개인 DB 중심 구조

예전 세상의 DB는 대기업이 운영하는 소수의 거대 DB였다. "모두가 자기 DB를 갖는다"는 초기 비전은 코드를 못 쓰면 DB로 할 일이 없어 납득되지 않았다. "모든 인류가 삶을 담은 Supabase DB를 갖게 되나?"라는 물음에 코플스톤은 "진심으로 그러길 바란다"고 답했다. AI를 쓰는 모든 사람이 어떤 형태로든 빌더가 된다.

코플스톤은 Supabase를 '인덱스 컴퍼니'라 부른다. 확인 필요 YC 배치의 모든 스타트업을 고객으로 삼으려 한 것은 새 사업이 태어나는 첫날 그 자리에 있기 위해서였다. 이제 그 대상이 개인 빌더로 넓어진다. DB 회사의 소비자 직판은 예전엔 '문법 오류'처럼 들렸지만, 개인 DB는 스타트업처럼 커지지 않아도 평생 쓰인다.

수십억 개 DB의 아키텍처

프로토타입에서 페타바이트까지

그림으로 보기: 코플스톤의 산수

DB 하나마다 전용 VM과 메모리를 주는 방식으로는 감당할 수 없다. 대부분의 프로토타입에는 '페라리'가 필요 없다. 그래서 Supabase는 Postgres와 SQLite 모두와 호환되는 Turso를 인수했고, 이를 바탕으로 시작 단계용 티어 Supabase Spark를 내놓는다.

그림으로 보기: 두 끝의 스펙트럼

Postgres는 MVCC와 확장 기능을 갖춘 클라이언트-서버 RDBMS로, 인스턴스 하나를 띄우는 데 메모리와 프로세스가 든다. SQLite는 별도 서버 없이 파일 하나에 내장되는 초경량 DB다. 같은 경험으로 시작해 페타바이트까지 키우겠다는 것이지만 구체적인 이전 방식은 설명되지 않았다.

첫날의 전략

AWS와 Stripe의 길

DB 회사는 오라클처럼 빨리 엔터프라이즈로 가는 것이 정석이었다. Heroku는 최고의 개발자 경험으로 시작했지만 커진 고객을 붙잡는 간극을 메우지 못했다. 초기 시장이 이렇게 커지면 엔터프라이즈가 필요 없지 않느냐는 물음에 코플스톤은 답했다. "우리는 다 원한다."

롤모델은 AWS와 Stripe다. 코플스톤은 들은 통계라며 틀릴 수 있다는 단서를 달았다. AWS 매출의 약 40%가 AWS에서 시작해 커진 스타트업에서 나온다는 것이다. 확인 필요

DB를 한 번 고르면 다른 제공자로 옮기는 일은 "거의 불가능"하다. 그래서 승부는 모든 프로젝트가 시작되는 첫날 그 자리에 있는 것이다. 어려운 점은 그 첫날의 모습이 빠르게 바뀐다는 것이다. 예전 첫날은 YC 배치의 기술 스타트업이었고, 이제는 모두가 빌더다.

에이전트를 위한 설계

에러 메시지와 eval

그림으로 보기: 에이전트 획득의 2단계

전통적인 에러 메시지는 `500 Internal Server Error`처럼 무언가 잘못됐다는 것만 알렸다. Supabase는 에러 메시지 안에 어떻게 고칠지, 어떤 문서를 읽을지를 그대로 적는다. 사용 사례를 하나씩 골라 에이전트가 한 번에 작업을 끝낼 때까지 고친다. 에러 메시지는 에이전트에게 주는 문서이자 프롬프트다.

엔지니어링의 중심은 평가(eval)로 옮겨 갔다. 주요 모델이 Supabase 위에서 앱을 얼마나 잘 만드는지 보여 주는 eval 웹사이트와 사내 eval 스위트를 운영하고, Postgres 자체를 어떤 모델이 잘 다루는지 벤치마킹해 모델이 쓸 스킬을 만든다.

사내 도입과 테스트

정책 없는 도입

그림으로 보기: 사내 설문

Supabase에는 AI 사용 정책이 없다. 원하는 도구는 다 준다. 도입이 늘어난 것은 지시가 아니라 모델이 훨씬 더 좋은 일을 훨씬 더 많이 한다고 엔지니어들이 스스로 확신했기 때문이다. 사내 작업도 바이브 코딩 수준이 아니라 강도 높은 일이다.

병목은 코드 작성에서 테스트의 양과 검증 도구로 옮겨 갔다. YC 배치에서도 Blacksmith, Depot 같은 고속 CI와 Greptile 같은 AI 코드 리뷰 도구가 크게 성장하고 있고, 같은 영역의 Ubicloud도 함께 거론된다. Ubicloud의 YC 출신 여부는 확인 필요

개인 에이전트와 도그푸딩

코드를 보지 않는다

코플스톤은 비서가 일주일 자리를 비운 사이 개인 에이전트가 무엇을 할 수 있는지 알게 되었고, 그 뒤로 개인 에이전트를 위해 만드는 일에 "집착"하게 되었다.

"사람 개발자가 코드 우선 환경에서 일하도록 돕는 것처럼 말하지만, 실은 에이전트를 위해 그렇게 하고 있다. 그 사람들은 머지않아 직접 상호작용하지 않을 것이다."

그는 'dots'라는 음성 에이전트와 하루 종일 통화하듯 대화하며 수정을 지시한다. 확인 필요 코드를 보지 않고 아키텍처도 확인하지 않으며, GitHub 경로 같은 힌트도 주지 않는다. 1년 뒤 일반 사용자가 겪을 경험을 오늘 미리 겪는 것이다.

진행자는 Supabase Select 컨퍼런스에 자기 대신 개인 에이전트를 보내 신기능을 듣고 코드베이스에 통합하게 하자는 상상을 꺼냈다. 에이전트만 입장하는 컨퍼런스, 청중석의 에이전트에게 마크다운을 에어드롭하는 행사, 이름은 '아티팩토리'라는 농담이 이어졌다.

Gbrain과 검색

올바른 해리 포터 세 권

그림으로 보기: Garry Tan의 전환

100만 토큰 컨텍스트는 해리 포터 3권 분량의 거대한 작업 기억이다. 그래도 에이전트에게는 제한적이다. 진짜 어려운 것은 어느 순간에든 올바른 세 권을 컨텍스트에 두는 일, 곧 검색이다.

Garry Tan은 자신의 모든 소통을 담은 마크다운 파일 약 50만 개, 30~40GB를 가지고 있다. 확인 필요 에이전트가 필요한 정보는 그중 1~2페이지다. Gbrain은 RAG 벡터 검색과 SQL 기반 동적 그래프 DB를 결합해 비정형 데이터에서 구조를 만든다. 한 진행자는 이 동적 스키마가 예전 팔란티어를 떠올리게 한다고 했다. 확인 필요

호스팅으로 Supabase를 고른 이유는 큰 임베딩과 관계형 데이터를 빠르게 다루고 오토스케일링이 잘 되는 Postgres이기 때문이다. 설계는 Claude Code에서 Exa로 RAG, 그래프 DB, 텍스트 검색 논문을 모아 요약하게 해 얻었다. 요즘이라면 AlphaSignal 같은 도구도 쓸 수 있다고 했다. 확인 필요

데이터베이스는 본질적으로 검색 메커니즘이다. 같은 검색에 10초가 걸린다면 에이전트를 루프에 돌려 1초 안에 돌려주는 새 인덱스를 찾게 하면 된다.

이 아이디어를 '데이터베이스의 미래' 저녁 모임에서 들었다고 소개한 사람은 코플스톤으로 보인다. 확인 필요 Garry Tan은 정말 똑똑한 코드 생성이 가능해지면 동적 검색은 분명히 온다고 공감했다.

원시적인 RSI

그림으로 보기: Gbrain의 자율 개선 루프

Cappy의 'Captains' 체제로 상시 가동되는 에이전트 둘을 둔다. 확인 필요 하나는 새 평가 범주를 계속 발굴하고, 다른 하나는 모든 범주를 돌며 매일 점수를 올릴 방법을 찾는다.

Garry Tan은 이것을 특정 검색 영역에 국한된 "매우 원시적인 형태의 재귀적 자기개선"이라 부른다. 목적과 트레이스만 바꾸면 모든 검색 시스템에 적용된다. 미래의 빌더도 이런 eval을 알아야 하느냐는 물음에는 "아마 아닐 것"이라 답했다. 지금의 실험은 모든 빌더가 꺼내 쓸 프리미티브를 발명하는 과정이다.

코딩의 미래

대화만으로 만든다

Claude Code를 만든 보리스 체르니가 그린 궁극의 코딩은 친구와 이야기하듯 Claude와 대화하면 Claude가 만드는 법을 찾아내는 상태다.

코플스톤은 갖고 있던 openusd.dev 도메인을, Stripe와 Visa 등이 'Open USD'를 발표하자 쓰기로 했다. 시간이 없던 그는 dots와 대화하며 생태계 개발자 사이트를 만들었다. 잠자리에서 휴대폰으로 "정보 아키텍처가 마음에 들지 않으니 개선안을 제안해 줘", "좋아, 그대로 구현해 줘"라고 말하자 20초 뒤 작업이 끝났고, 글과 링크와 SEO까지 되어 있었다.

한 진행자는 모델 가중치에 들어가기 전까지는 약간의 마크다운이 필요하다며 Garry Tan으로 보이는 이 진행자 확인 필요 는 지금을 이렇게 진단했다.

창업의 경제학과 조언

돈이 필요 없는 축복

Garry Tan으로 보이는 진행자 확인 필요 는 버티컬 SaaS의 혹한기를 말했다. 9~12개월 전에는 ARR 500만~1,000만 달러면 시리즈 A가 거의 보장되었지만 지금은 투자자 관심이 적다. 확인 필요

그런데 이제 10~15명으로 1,000만~1,500만 달러, 때로는 2,500만~5,000만 달러 ARR에 이르고 매우 수익성이 높다. 확인 필요 시리즈 A를 못 받아 낙담한 창업자에게 그는 "돈이 필요 없으니 돌아보면 축복일 것"이라고 말한다.

15명이 1인당 200만 달러 ARR에 마진 50%라면 모두가 연 100만 달러를 버는 셈이다. 확인 필요

예전에는 큰 펀딩이 명예의 배지였다. 코플스톤은 이제 투자를 받지 않는 것이 대단한 성취처럼 느껴진다고 말한다.
