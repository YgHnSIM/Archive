여섯 가지 핵심 명제

  1. 아키텍처의 입력은 세 동인이다. 기능 요구(무엇을), 품질 속성(얼마나 잘), 제약(어떤 조건에서). 품질 속성에는 우선순위를 매기고, 제약에는 매기지 않는다.
  2. 같은 기능, 다른 구조, 다른 품질. 쇼핑 웹 앱을 모놀리스로 짜든 3계층으로 짜든 기능은 같다. 하지만 수정 용이성·보안·성능·개발 속도의 성적표는 엇갈린다.
  3. 비기능 요구가 모두 품질 속성은 아니다. 기준은 시스템 전체의 성질이면서 아키텍처적으로 중요한가다. 글자 색은 빠지고, 사용성은 들어온다.
  4. 요구와 아키텍처는 서로 밀고 당긴다. 한 도시를 전제로 짠 우버의 구조는 여러 도시 요구를 감당하지 못해 DISCO로 바뀌었다.
  5. 제약은 협상하지 않되 이유를 남긴다. 이유, 관련 여지, 대안, 제약을 낸 이해관계자의 네 항목으로 기록한다.
  6. 체크할 수 없는 요구는 입력이 아니다. 6부분 품질 속성 시나리오(근원·자극·대상·환경·응답·응답 측정)로 모호한 문장을 시험 가능한 요구로 바꾼다.
1

컨텍스트 다이어그램에서 아키텍처 요구로

질문이 동인이 되는 순간

2강의 컨텍스트 다이어그램은 범위, 사람 행위자, 외부 실체를 분명히 한다. 그런데 그림을 그리면 곧바로 질문이 생긴다. 사용자는 몇 명인가? 일정 시간에 거래가 몇 건이고 피크 부하는 어느 정도인가? 저장 요구는 얼마나 큰가? 외부 시스템과는 API 호출, 공유 저장소, 메시지 큐 가운데 무엇으로 연결하며, 동기인가 비동기인가?

이 질문들이 모여 아키텍처 요구가 된다. 기능 목록이 아니라 시스템의 크기, 통신 방식, 튼튼함을 정하는 질문들이다. 3강은 이 질문을 설계에 쓸 수 있을 만큼 정밀하게 받아 적는 법을 다룬다.

2

같은 기능, 다른 구조, 다른 품질

온라인 쇼핑 웹 앱: 모놀리스 대 3계층

쇼핑 웹 앱을 두 구조로 만들 수 있다. 모놀리스는 화면·업무 논리·데이터 접근을 한 프로세스에 묶는다. 3계층은 UI 계층, 업무 논리 계층, 데이터 접근 계층으로 나눈다. 둘 다 기능 요구는 모두 충족한다. 갈리는 것은 품질이다.

속성모놀리스3계층근거
수정 용이성불리유리화면(자바 서블릿 → React), 규칙(장바구니 품목 수), DB(SQL ↔ NoSQL)를 층별로 교체
보안학생 관점: 유리강사 선택: 유리모놀리스는 중간자 공격 지점이 적다. 3계층은 데이터 계층을 따로 지키고 층별로 보안 강도를 달리하며, 백엔드를 방화벽으로 감쌀 수 있다
성능유리불리모놀리스는 프로세스 안 메서드 호출. 3계층은 IPC·네트워크와 층별 보안 처리가 더해진다
개발 속도불리유리3계층은 인터페이스만 정하면 병렬 개발. 모놀리스는 강하게 묶여 나누기 어렵다

결론은 둘이다. 모든 품질 속성에서 동시에 최고인 구조는 없으므로 트레이드오프와 우선순위가 필요하다. 그리고 기능 요구가 가장 먼저이지만, 그것만으로는 충분하지 않다.

3

‘비기능 요구’와 품질 속성의 경계

그리고 사용성 논쟁

품질 속성을 흔히 ‘비기능 요구’라 부르지만, 강의는 이 말에 문제가 있다고 본다. ‘비기능’은 기능이 아닌 모든 요구를 가리키기 때문이다. “화면 글자 색은 파란색”은 기능 요구도 아니지만 품질 속성도 아니다. 구조에 아무 영향을 주지 않는 UI 디자인 요구일 뿐이다. 그래서 모든 비기능 요구가 품질 속성은 아니다.

품질 속성의 기준은 둘이다. 시스템 전체의 성질이면서 아키텍처적으로 중요해야 한다. 곧 “아키텍처를 바꿔서 그 성질을 높일 수 있는가”를 묻는다.

사용성은 품질 속성인가

사용성을 ‘있으면 좋은 것’으로 보는 시각도 있었지만, 차량 호출 앱에서 사용성이 나쁘면 고객을 잃는다. 그리고 사용성은 구조로 높일 수 있다. 강의가 든 다섯 경로는 다음과 같다.

  1. 기능 간 일관성: 운전자 화면과 승객 화면, 호출과 음식 배달의 흐름을 일관되게 하려면 모듈화와 재사용성이 필요하다.
  2. 일관된 오류 처리 전략.
  3. 캐싱과 미리 가져오기로 정보를 제때 보여 준다.
  4. 응답성: 버튼을 누른 순간부터 응답까지의 전체 지연. CDN과 데이터 모델 설계까지 아키텍처 문제다.
  5. 인증 흐름: SSO냐 다중 인증이냐도 아키텍처 결정이며 사용성을 좌우한다.

그러므로 사용성은 분명한 품질 속성이다. 동적 UI의 개인화도 사용성의 일부로 본다.

그림으로 보기: 세 동인과 아키텍처

기능 요구를 포착하는 법

유스케이스, 사용자 스토리, 기능 설명, 운영 설명, 형식 명세 등 형식은 무엇이든 좋다. 중요한 것은 다음 다섯 가지를 명시적으로 적는 것이다.

  1. 사전 조건과 가정
  2. 정상 흐름(happy path)
  3. 대체 흐름: 예) 로그인에서 아이디·비밀번호가 틀렸을 때
  4. 오류 조건: 예) 비밀번호를 확인할 DB에 접근할 수 없을 때
  5. 사후 조건

업무 분석가가 기능 요구를 정리할 때 아키텍트도 함께 들어가, ‘-ilities’에 관한 질문을 던지고 품질 속성의 우선순위까지 받아 적는다.

우버 사례: 요구와 아키텍처의 주고받음

강의에 따르면 우버는 처음에 “한 도시에만 배포한다”는 전제로 매칭 알고리즘을 짰다. 여러 도시를 동시에 처리하라는 요구가 들어오자 기존 구조로는 응답 시간이 길어져 성능과 사용성이 무너질 상황이었다. 선택지는 아키텍처를 바꾸거나 요구를 포기하는 것뿐이었고, 우버는 구조를 바꿨다. 그 결과가 DISCO다. 지역을 셀로 쪼개 매칭 알고리즘이 각 셀만 고려하게 했고, 운전자 가용 상태를 받아 오는 방식과 호출을 뿌리는 방식까지 바뀌었다.

[해설] 외부 사실. 우버(당시 UberCab)는 2010년 6~7월경 샌프란시스코에서 서비스를 시작했다. DISCO는 Dispatch Optimization의 약자로, 2015년경 Matt Ranney의 발표로 공개됐다. 셀 분할에는 Google S2를 썼고, 우버의 자체 격자 H3는 그 뒤에 나왔다. 여러 도시 확장은 재작성의 중요한 동기 가운데 하나였다.

교훈은 작은 시스템에도 해당한다. 처음부터 확장 가능하게 잡아 두면 새 기능 요청을 매끄럽게 받을 수 있다.

두 번째 동인: 제약

어디서 오고, 어떻게 기록하나

제약은 늘 있다. 기존 시스템에 기능을 더할 때, 상용 구성 요소(LLM 포함)를 가져다 쓸 때, 시장의 힘(오래된 자바 서블릿은 받아들여지지 않음)이 작용할 때, 그리고 우리가 편하자고 고른 도구(LangChain의 LangGraph)까지 제약이 된다.

강의의 분류: 제약의 네 종류

종류강의 속 예
기술회사가 AWS를 쓰면 새 기능도 AWS 위에서 설계
사업(가상 예) 대학이 Azure 라이선스를 샀으니 AWS는 쓰지 않음
프로젝트예산, 인력, 일정, 팀의 기술 역량
규제개인정보 보호를 위한 GDPR 준수

출처 주의. 이 네 분류와 “비기능 요구와 품질 속성은 다르다”는 입장은 이 강의의 설명이다. 『Software Architecture in Practice』나 SEI 문헌에서 같은 네 분류를 명시한 문장은 찾지 못했다 (확인 필요).

우선순위는 없고, 기록은 네 항목

제약은 모두 같은 무게로 따라야 하므로 우선순위를 매기지 않는다. 대신 배경을 잃지 않도록 네 항목으로 기록한다.

항목가상의 Azure 제약 예
이유대학이 Azure 라이선스를 샀고, 다른 클라우드는 추가 비용이 든다
관련 여지Azure 자체는 못 바꾸지만 그 안에서 필요한 서비스만 고를 수 있다
대안저장 공간 제한이 있는 월 200 정도의 AWS 요금제를 검토
제약을 낸 이해관계자대학

제약 자체는 협상할 수 없지만, 울타리 안에서 무엇을 고를 수 있는지가 ‘관련 여지’다.

세 번째 동인과 모호한 품질 요구

체크할 수 없으면 입력이 아니다

품질 속성은 찾아내기도, 시험 가능하게 적기도 어렵다. 업계에서 흔한 문장들을 보자.

  • 시스템은 모든 동작에 0.5초 이내로 응답해야 한다.
  • 시간이 중요한 기능은 충분한 성능을 가져야 한다.
  • 장애의 영향은 최소화되거나 제거되어야 한다.
  • 고객별 맞춤 룩앤필.

숫자가 있는 첫 문장조차 모호하다. ‘모든 동작’이 무엇인지, 어디서 어디까지 재는지, 큰 파일 업로드나 전체 검색에도 0.5초인지 알 수 없다. “쉽게 쓸 수 있어야 한다”, “수정 가능해야 한다”도 어떤 측면인지 빠져 있다.

차량 호출 플랫폼이라면 응답 시간을 수치화하고, 어느 지역·어떤 사용자(예: 2마일도 안 되는 짧은 이동)인지 정하고, 그러려면 배차 알고리즘이 수정 가능해야 한다는 것까지 짚어야 한다. 품질 속성은 정확히 무엇인지, 사업적으로 왜 중요한지, 측정·시험 가능한지가 분명해야 한다. 그렇지 않으면 완성 후 요구가 충족됐다고 체크할 수 없다.

모호함을 번역하는 틀: 6부분 품질 속성 시나리오

보안·성능·수정 용이성 연습

6부분 품질 속성 시나리오는 과목 교재 『Software Architecture in Practice』에 실린 틀이다. 강의는 SEI가 보쉬(Bosch)에 컨설팅하며 만든 틀이라고 했다 (확인 필요). 이 기원을 뒷받침하는 자료는 찾지 못했고, 확인된 것은 교재 2판(2003)에서 체계적으로 소개됐다는 점이다.

응답탐지·거부, 상관 ID와 함께 기록, 안전하고 일반적인 오류 반환, 무단 SQL 실행 차단, 성능 저하 없이 운영경보를 울림고칠 곳 식별·수정·시험·배포
응답 측정성공한 인젝션 0건, 입력 검증·매개변수화로 100% 차단, 1초 안에 상세 기록, 데이터 손상·무단 접근·중단 없음피크 시간에도 0.5초 이내1인월 안에, 아키텍처 변경 없이
  • 연기 감지기 문장은 여섯 칸이 모두 들어 있어 잘 쓴 요구다. 강의는 다루는 속성을 성능과 안전 둘 다로 정리했다. 측정이 0.5초라는 점에서 성능이 드러난다.
  • 수정 용이성은 시간이 아니라 변경 비용(인력, 기간)과 변경 용이성(수정 지점 수, 파급 효과, 부작용)을 본다. 무엇이, 왜, 언제, 누가 바꾸는지를 정해야 한다. 누가 바꾸느냐(설정만 바꾸는 시스템 엔지니어인가, 코드를 고치는 엔지니어인가)에 따라 구조가 달라진다.
  • 1인월과 한 달은 같지 않다. 1인월은 작업량이므로 두 사람이 반 달 일해도 1인월이다.

맺음말

여섯 가지 핵심 통찰

  1. 같은 기능도 구조에 따라 품질이 갈리므로, 품질 속성에는 우선순위가 필요하다.
  2. 품질 속성의 기준은 “기능이 아니다”가 아니라 “구조를 바꾸면 달라지는가”다.
  3. 요구와 아키텍처는 한 방향으로만 흐르지 않는다. 그래서 아키텍트가 요구 수집 단계에 들어간다.
  4. 제약은 협상하지 않되, 이유·여지·대안·이해관계자를 남긴다.
  5. 체크할 수 없는 요구는 아키텍처의 입력이 아니다. 특히 환경과 응답 측정이 정해져야 시험 가능해진다.
  6. 수정 용이성은 무엇을, 왜, 언제, 누가 바꾸는가의 문제다.
