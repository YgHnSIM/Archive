한눈에 보기

여섯 가지 실천 원칙

  1. 검증 루프를 닫아라. 코드를 실행하고 트레이스를 모으지 못하는 에이전트는 믿을 수 없다.
  2. 지도를 만들어라. feature map 없는 지능은 길을 잃는다.
  3. 스킬도 단위 테스트하라. 이벌과 교차 심판, /loop로 10점을 향해 오른다.
  4. 로컬에서 관찰한 뒤 확장하라. 신뢰 없이 클라우드 에이전트를 수백 개 띄우면 토큰만 탄다.
  5. 강한 제약으로 막아라. 프롬프트는 잊힌다. 나쁜 코드는 빌드에서 거부되어야 한다.
  6. 비엔지니어가 출시하게 하라. 가드레일이 단단하면 PM과 디자이너도 프로덕션에 낸다.

[해설] 위 문구는 해설자의 요약이며 직접 인용이 아니다.

세 갈래의 도입부

동료, 페어 프로그래머, React 도구

같은 발표가 서로 다른 세 도입부로 공개되었다.

  • 에이전트를 동료처럼. GrokBot 확인 필요을 만들 때 "에이전트가 정말 동료에 가깝다면?"이라는 관점을 취하고 싶었다고 말한다. 자는 동안 버그를 고치게 하는 상주형 봇 실험의 계기였다.
  • AI는 페어 프로그래머. AI를 가장 잘 쓰는 방법은 페어 프로그래밍 상대로 쓰는 것이지, 코드 작성을 대체하거나 생각을 외주화하는 것이 아니라고 말한다. "이번 주 PR 100개" 같은 압박을 풍자하고(실제 수치가 아닌 풍자적 예), 코드 작성 시간은 줄었지만 AI가 한 일을 리뷰하고 고치는 시간이 늘었다고 털어놓는다. 이 장면이 본 발표와 같은 시기의 발언인지는 확인 필요
  • React 도구 출시 장면. 청중에게 "매우 흥미로운 이정표"를 발표하며 "Babel plugin React"와 새 ESLint 플러그인 설치를 안내하는 장면이다. React Conf 2025 첫날 키노트의 React Compiler 1.0 발표와 맞으며, 외부 자료상 이 발표는 로런 탄이 했다.

[해설] "생각을 외주화하지 말라"는 경고와 "아침에 보니 PR이 머지되어 있었다"는 장면은 모순이라기보다, 관찰과 제약 위에서만 자율을 허용한다는 일관된 태도로 읽힌다.

신뢰 곡선과 자동 머지

마이크로매니징에서 사후 리뷰로

핵심 질문은 "에이전트를 어떻게 신뢰할 것인가?"다. 에이전트가 "결정적 단서를 찾았다"며 엉뚱한 진단을 백 번째 내놓으면 신뢰는 무너지고, 엔지니어는 팀원 등 뒤에서 모니터를 지켜보는 매니저처럼 마이크로매니징으로 돌아간다. 에이전트 하나를 믿지 못하면 100개를 띄울 수 없다.

그림으로 보기: 신뢰 곡선

지난 5개월 동안 곡선을 올라온 그는 이제 에이전트가 PR을 자동 머지하게 해 두었다. "slop artist"처럼 들릴 수 있다고 웃으며, 발표 당일 아침 PR 20개쯤이 이미 main에 머지되어 있었고 main에서 리뷰해 보니 좋았다고 말한다.

검증과 control glass

"당신이 검증자이자 병목이다"

가장 중요한 단 하나의 스킬은 검증이다. 단언문 몇 개가 아니라, 코드를 실행하고 CPU 트레이스나 힙 스냅샷을 뜨고 iOS 시뮬레이터를 여는 것, 즉 사용자에게 노출되는 방식 그대로 실행하는 것이다.

입사 첫 주, 그는 출시를 일주일 앞둔 에이전트 창 팀의 성능 작업을 도왔다(출시 대상은 agents window). Chrome DevTools로 트레이스를 뜨고 플레임 그래프를 보며 스크린샷을 에이전트에게 보냈지만, 에이전트가 자신 있게 지목한 원인은 진짜가 아니었다. 그는 스크린샷을 찍고 로그를 붙여넣는 동안 엔지니어 본인이 검증자이자 병목이라는 것을 깨달았다.

그림으로 보기: 검증 루프 닫기

그래서 처음 만든 스킬이 control glass다. 'glass'는 Cursor 안에서 Agents Window를 가리키던 코드명이다. Electron, 웹, iOS 어디서든 CDP나 시뮬레이터 제어 유틸리티로 에이전트가 앱을 구동하고 클릭하고 트레이스를 모으게 할 수 있다.

그림으로 보기: 올바른 코드와 좋은 코드

feature map

지능을 길 잃지 않게

앱을 띄울 수 있게 되자 새 한계가 드러났다. 에이전트는 자신이 띄운 앱이 무엇을 하는지, 기능이 어디 있는지 몰랐다. "왼쪽 사이드바가 버벅인다"는 보고에 코드베이스 전체를 그렙하며 헤맸다.

그림으로 보기: feature map의 구성

사내 Slack 피드백 채널에는 스크린샷 한 장에 "???"만 적힌 보고도 올라온다. feature map이 있으면 에이전트는 앱을 어떻게 탐색할지 훨씬 많은 맥락을 갖는다.

그림으로 보기: "???"를 코드로

pstack에는 이 인프라를 만드는 create verification과 앱 변화에 맞춰 지도를 갱신하는 maintain verification 스킬이 들어 있다.

pstack과 /how

관찰에서 태어난 스킬

pstack의 P는 '감자 부대(potato sack)'다. Y Combinator CEO 개리 탄(Garry Tan)의 gstack을 패러디한 이름이고, 성은 같지만 친척은 아니라고 농담한다.

에이전트는 "이건 분명 이것 때문"이라고 단언하곤 했다. 도구 호출 목록을 역추적해 보니 관련 코드를 읽지도 않았다. 그래서 만든 것이 /how 스킬이다.

그림으로 보기: /how 스킬의 탄생

그는 이를 코딩은 뛰어나지만 맥락이 없는 신입을 온보딩하는 일에 빗댄다. 마크다운 스킬은 텍스트 파일일 뿐이지만 에이전트를 "더 똑똑한 잠재 공간"으로 끌어당긴다.

이벌과 /loop

에이전트의 단위 테스트

제품이 계속 바뀌는데 스킬은 어떻게 유지하고, 검증 루프는 어떻게 믿는가? 로런 탄의 답은 이벌은 에이전트의 단위 테스트라는 것이다. pstack의 potato mode 아래 eval playbook에 꽤 엄격한 절차가 있다.

그림으로 보기: 이벌 플레이북

평가받는다는 것을 알면 에이전트는 행동을 바꾸므로 서브에이전트의 디렉터리 이름을 위장한다. 코디네이터의 채점 편향은 다른 기저 모델의 심판으로 교차 검증한다.

그림으로 보기: 평가 맥락 숨기기

control glass와 그 CLI도 거의 손대지 않고 /loop 힐클라이밍으로 만들었다. 처음엔 반복이 많이 필요했다. 스킬 유지에는 안목과 관찰이 필요하다. 페어 프로그래밍하듯 "왜 이렇게 안 했어?"라고 묻는 뒷좌석 운전자가 되어 도구 호출, 코드, 사고 블록을 열어 보라는 것이다.

재작성과 Dune

인간 슬롭의 교훈

Meta 같은 모노레포에는 수만 명이 코드를 넣고, 품질은 생각만큼 환상적이지 않다. "AI 슬롭 전에 인간 슬롭이 있었다". 그래서 빅테크 인프라는 가장 미숙한 엔지니어도 프로덕션 DB를 날리지 못하게 설계되었고, 에이전트도 그 안에서 잘한다.

그림으로 보기: 브라운필드와 그린필드

Cursor 팀이 전날 출시한 GrokBot 확인 필요의 초기 프로토타입도 빠르게 바이브 코딩되었다. 로런 탄은 GrokBot 전체를 새 아키텍처로 리팩터링하는 데 PR 600개 이상을 썼다. 지금은 코드를 거의 보지 않는다고 한다. GrokBot을 재작성하며 구축한 프레임워크가 Dune, Electron을 위한 일종의 Next.js로, 처음부터 에이전트가 코드를 쓴다고 전제했다.

그림으로 보기: Dune의 강한 제약

주석 금지는 에이전트가 "Lauren이 이렇게 하지 말라고 했다" 같은 대화 파편을 주석으로 남기기 때문이다. 렌더러가 매 프레임 16ms 안에 그려야 하므로 main과 renderer의 교차 임포트는 CI에서 실패한다. 에이전트 창에는 아직 이 구조가 없어 성능이 자주 퇴행한다고 한다.

그림으로 보기: 강제의 계층

PR 크기에는 상한이 없지만(50줄이나 수백 줄에서 1,000줄까지) 원자적으로 쪼개라고 한다. Git 히스토리는 에이전트에게도 가장 풍부한 맥락이다. 가상화에는 Cheng Lou의 Pretext를 쓴다.

[해설] 가장 짧은 경로가 가장 좋은 경로가 되게 하라. 이 귀찮음은 에이전트가 흡수한다.

토큰 ROI와 에이전트 팀

비기술직의 "Cursor 모먼트"

토큰이 무제한인 곳이 아니어도 가능한가? 로런 탄은 특권적 환경임을 인정하면서 ROI의 문제라고 답한다. 1만 명 조직의 기획 오버헤드도 비용이다(Meta처럼 되고 싶지 않다고 말한다). 가드레일을 깔면 가장 단순한(dumbest) 에이전트도 잘 쓴다("fable size"가 아닌 에이전트도, 뜻 확인 필요).

그림으로 보기: 토큰 ROI

그는 발표 당일 나온 Grok 4.6이 지능은 높고 토큰당 비용은 4.5와 같다고 "믿는다"고 했다. Cursor와 SpaceX AI가 추구하는 것은 비용 대비 지능의 파레토 프런티어다.

Cursor 팀이 전날 선보인 GrokBot은 비기술직에게 찾아온 "Cursor 모먼트"다. GrokBot은 iMessage 같은 대화형 UI로, 에이전트에게 이름을 붙이고 사람처럼 팀을 꾸린다. 계정마다 에이전트를 두거나, PM이라면 Lauren이 어젯밤 한 일을 요약하는 에이전트를 둘 수 있다. PM이 "버그 고쳤는데 봐 줄래요?"라고 하면 리뷰해 보고 그대로 승인하는 일이 잦다.

그림으로 보기: 에이전트 팀

엔지니어의 가치는 타이핑 속도가 아니라, 에이전트 군단이 일탈하지 않도록 신뢰의 인프라와 가드레일을 설계하는 매니저의 역량에 있다.
