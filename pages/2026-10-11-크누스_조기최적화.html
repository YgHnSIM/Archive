격언은 누구의 말인가

크누스, 호어, 데이크스트라

원문은 이 격언이 성능 문제를 미루는 근거로 널리 쓰인다고 말합니다. 구글 Ngram 뷰어(책 속 단어 빈도를 연도별로 보여 주는 도구)로 보면 이 표현은 1974년 이전에는 사실상 없다가 1974년부터 급증합니다.

시점사건
1974년 12월크누스가 ACM Computing Surveys 제6권 제4호의 41쪽 논문 『Structured Programming with go to Statements』에서 코드 예제와 함께 처음 활자화
1989년크누스가 『The Errors of TeX』에서 이 말을 "C.A.R. 호어의 격언"이라고 부름
2003년호어가 한스 거위츠에게 보낸 서신: "이 인용구가 어떻게 나왔는지 전혀 기억나지 않습니다. 제가 에츠허르 데이크스트라(Edsger Dijkstra)의 발언으로 돌렸을 수도 있습니다."
2004년리코 마리아니(MS 리서치)의 질문에 호어가 "내 말투 같기는 한데, 좋은 도서관에서 몇 시간만 뒤져보면 원래 출처를 찾을 수 있을 것 같네"라고 답함

데이크스트라는 2002년에 세상을 떠나 더 확인할 수 없습니다. 무라토리는 최초 발언자보다 세 사람의 공통 궤적이 중요하다고 봅니다. 셋 다 1960년대 초 ALGOL 컴파일러를 직접 만들었습니다.

인물출생튜링상이 논쟁에서의 역할
Edsger Dijkstra1930년1972년1968년 GOTO 논쟁 촉발, EWD249로 구조적 프로그래밍 제창
Tony Hoare1934년1980년Elliott 503 컴파일러 성능 참사(초당 2자), 데이터 추상화 정립
Donald Knuth1938년1974년1974년 논문 집필, 97% 대 3% 격언과 실증 프로파일링 공식화

1968년 GOTO 논쟁

데이크스트라의 편지와 바뀐 제목

1967년 제1회 ACM 운영체제 원리 심포지엄(SOSP)에서 데이크스트라는 6인 팀과 만든 THE 멀티프로그래밍 시스템을 발표했습니다. 원문은 이 논문이 세마포어(공유 자원 접근을 조율하는 신호 변수), 상호 배제 같은 동시성의 기본 원리를 한자리에 정립했다고 씁니다.

발표 뒤 휴게실에서 그는 GOTO 문이 프로그램 추론을 어렵게 만든다고 불평했고, 동료들의 권유로 CACM에 원고를 냈습니다.

단계제목
원래 원고A Case Against the GO TO Statement
1968년 3월 CACM 게재Go To Statement Considered Harmful (원문에 따르면 편집을 맡은 니클라우스 비르트가 심사를 건너뛰고 독자 투고란으로 돌리며 제목을 바꿈)

항의 편지가 쏟아졌고, 데이크스트라는 "사람들이 GOTO를 종교로 만들어버렸다"고 개탄했습니다. 같은 해 아인트호벤 공대 수학과는 프로그래밍이 진정한 수학이 아니라며 그의 팀을 해산했고, 그는 심한 우울에 빠졌습니다.

소프트웨어 위기와 IBM 광고

하드웨어는 빨라지고, 소프트웨어는 그대로

1960년대 말 하드웨어의 속도와 메모리는 빠르게 커졌지만 소프트웨어 개발은 1950년대식 수작업에 머물렀습니다. 프로그램이 커지면 일정이 늦어지고 예산이 폭증했습니다. 원문은 이를 '소프트웨어 위기'라 부르며, 당시 업계에서 이 말을 공개적으로 하는 것이 금기에 가까웠다고 씁니다.

데이크스트라에게 오래 남은 사례가 1968년 10월호 『Datamation』의 IBM PL/I 광고입니다. 문구는 "Can a young girl with no previous programming experience find happiness with PL/I?"였습니다. 원문은 이를 오늘의 '바이브 코딩'(AI에게 말로 지시해 코드를 만드는 방식) 과대광고에 견줍니다.

무라토리는 1968년 12월호 Datamation의 군 지휘통제 시스템 논문에서 실제 PL/I 코드를 찾았습니다. 32비트 워드 안에서 1비트 태그로 8비트 또는 5비트 데이터를 나누는 판별 유니온(태그로 내용 형태를 구분하는 자료형)을 선언하려고, 의미 없는 NULL 필드를 비트 단위로 계산하고 번호까지 붙여야 했습니다.

DECLARE 1 BUFFER,
          2 TAG BIT(1),
          2 NULL1 BIT(31),
        1 BUFFER_A DEFINED BUFFER,
          2 NULL2 BIT(1),
          2 DATA_8 BIT(8),
          2 NULL3 BIT(23),
        1 BUFFER_B DEFINED BUFFER,
          2 NULL4 BIT(1),
          2 DATA_5 BIT(5),
          2 NULL5 BIT(26);

당시 프로그래머 책상에는 모니터가 없었습니다. 코딩 용지에 연필로 쓰면 키펀치 오퍼레이터가 천공 카드로 옮겼고, 결과는 반나절 뒤에 받았습니다.

NATO 1968 회의와 EWD249

위기의 공식 인정과 데이크스트라의 회복

1968년 10월 독일 가르미슈의 NATO 소프트웨어 공학 회의에 약 50명이 모였습니다. 벨 연구소의 에드워드 데이비드와 알렉스 프레이저는 세션 7 발제에서 야망과 성취의 격차가 벌어지고 있고, 대규모 소프트웨어의 결함이 생명과 국가까지 위협한다고 말했습니다.

케네스 콜린스가 '위기'라는 말이 과하다고 하자, 더글러스 T. 로스가 반박했습니다.

"내가 지금 당장 심장마비로 쓰러져 죽어가고 있다면, 내 팔다리와 뇌와 소화기관이 정상 작동하고 있다는 사실 따위는 아무런 의미가 없다. 나는 명백히 치명적인 위기(Crisis) 속에 처해 있는 것이다!"

더글러스 T. 로스, 1968 (원문 인용)

데이크스트라는 전문가 집단이 소프트웨어 실패를 인정한 것이 "가장 신선하고 상쾌한 경험"이라고 화답했습니다. 1969년 8월 그는 『EWD249: Notes on Structured Programming』을 탈고했습니다. 핵심은 '단계적 프로그램 구축'입니다. 프로그램을 다 짠 뒤 증명을 덧붙이지 않고, 작성 과정 자체가 비공식 증명이 되게 합니다. 원문은 이 문건이 복사기를 타고 퍼진 이유를, 대가의 사고 흐름을 그대로 보여 줬기 때문이라고 봅니다.

호어의 컴파일러 참사와 1972년 책

초당 1,000자에서 초당 2자로

엘리엇 브라더스의 호어는 1963년 ALGOL 60 컴파일러를 납품했습니다. 그 뒤 30명이 투입된 Elliott 503 Mark II 프로젝트가 2년이 지나도 끝나지 않자, 호어는 컴파일러만 6개월 안에 먼저 내기로 했습니다.

시점컴파일 속도 (초당 글자 수)
기존 컴파일러 (1963년)500~1,000자
신형 첫 구동2자 (기존 1,000자 대비 99.8% 감소)
수개월 최적화 후8자 (첫 구동 2자 대비 4배)

프로젝트는 취소됐습니다. 호어는 1980년 튜링상 강연 『The Emperor's Old Clothes』에서 원인을 셋으로 짚었습니다.

  • 주기억장치 할당의 전체 계획이 없었습니다. 각 팀은 어딘가의 할당자나 오버레이(필요할 때 코드를 메모리에 교대로 올리는 방식)가 알아서 해 줄 거라 믿었습니다.
  • 시스템 소프트웨어가 코어 메모리를 다 차지해 사용자 프로그램 자리가 없었습니다.
  • 스래싱(페이지 교체가 끊이지 않아 일을 못 하는 상태)으로 CPU의 99%가 입출력 대기에 묶였습니다.

호어는 이후 로스의 Plex 개념을 받아들여 레코드(오늘의 구조체) 이론을 발전시켰습니다. 1972년에는 데이크스트라, 올레요한 달과 함께 『Structured Programming』(Academic Press)을 냈습니다. 데이크스트라는 제어 구조, 호어는 데이터 구조, 달은 SIMULA 67의 클래스를 다뤘습니다. 이 책을 받은 크누스는 세 저자에게 장문의 서신을 보내며 구조적 프로그래밍에 합류했습니다.

1974년 논문과 작업된 예제

격언이 나온 자리: 효율성을 다룬 3쪽

1969년 스탠퍼드에 온 크누스는 로버트 플로이드와 함께 1971년 "GOTO를 없앨 수 없는 제어 구조가 있다"는 논문을 냈습니다. 1974년 논문은 GOTO의 맹목적 금지를 비판하고, 고급 언어가 표현력과 실행 효율을 함께 갖추려면 어떤 제어 구조가 필요한지 다룹니다. 격언은 '효율성' 3쪽 섹션에 나옵니다.

예제 문제: 배열 A[1..m]에서 값 x를 찾습니다. 찾으면 빈도 카운터 C[i]를 1 올리고, 못 찾으면 m+1 자리에 x를 넣고 빈도를 1로 둡니다(ALGOL 전통에 따라 1부터 셈).

예제 1: GOTO를 쓴 단순 선형 탐색

for (i = 1; i <= m; i++) {
    if (A[i] == x) goto found;
}
m = m + 1;
A[m] = x;
C[m] = 0;
found:
C[i] = C[i] + 1;

예제 2: 보초법

보초(sentinel)는 탐색 전에 배열 끝에 찾는 값을 미리 써 두는 기법입니다. 그러면 루프 안에서 범위 검사(i <= m)가 필요 없습니다. 크누스는 GOTO 사용 여부보다 알고리즘이 본질이라고 봤습니다.

A[m + 1] = x;
i = 1;
while (A[i] != x) {
    i = i + 1;
}
if (i > m) {
    m = m + 1;
    C[m] = 1;
} else {
    C[i] = C[i] + 1;
}

예제 2a: 루프 언롤링과 GOTO의 복귀

루프 언롤링은 반복 한 번에 여러 원소를 처리하도록 본문을 펼치는 기법입니다. 크누스는 가장 중요한 내부 루프라면 2회씩 손으로 펼치고 GOTO를 다시 쓰겠다고 했습니다("Doubling Up").

A[m + 1] = x;
i = 1;
goto check;
loop:
i = i + 2;
check:
if (A[i] == x) goto found;
if (A[i + 1] != x) goto loop;
i = i + 1;
found:
if (i > m) {
    m = m + 1;
    C[m] = 1;
} else {
    C[i] = C[i] + 1;
}

크누스는 캐시 없는 다중 레지스터 컴퓨터를 가정하고 메모리 참조 횟수를 셌습니다(N은 루프 반복 횟수).

예제메모리 참조 횟수원문이 전하는 효과
예제 16N + 10기준
예제 2 (보초법)4N + 4루프 본문 6회에서 4회로, 실행 시간 33% 단축
예제 2a (언롤링)약 3.5N예제 2 대비 추가 12% 향상

"예제 2에서 2a로의 성능 향상은 12%에 불과하며, 많은 사람들은 이를 사소하다고 부를 것이다. ... 하지만 이것이 정립된 공학(Engineering) 분야였다면 12%의 개선은 결코 사소한 것으로 치부되지 않았을 것이다. 제트 엔진 효율이 12% 향상되었다면 아무도 코웃음 치지 않았을 것이다!"

Donald Knuth, 1974 (원문의 번역 인용)

"10% 개선" 가정의 계산

격언의 원문과 그 전제

원문이 옮긴 1974년 대목은 다음과 같습니다.

"프로그래머들은 프로그램의 비핵심적인 부분의 속도를 고민하느라 엄청난 시간을 낭비한다. 그리고 이러한 효율성 시도는 디버깅과 유지보수 관점에서 강력한 부정적 영향을 미친다.

약 97%의 상황에서는 작은 효율성에 대해 잊어버려야 한다. 조기 최적화는 모든 악의 근원이다.

하지만 우리는 저 결정적인 3%의 기회를 놓쳐서도 안 된다. 훌륭한 프로그래머라면 안일에 빠지지 않고 크리티컬한 코드를 면밀히 살펴볼 것이나, 이는 오직 그 코드가 명확히 식별된 이후여야 한다."

Donald Knuth (1974)

몇 문단 앞에 '3%'의 근거가 있습니다.

"경험에 따르면 I/O 바운드가 아닌 프로그램의 실행 시간 대부분은 소스 코드 텍스트의 약 3%에 집중되어 있다. 일반적으로 프로그램 전체의 속도를 지배하는 짧은 내부 루프가 존재하므로, 이 내부 루프의 속도를 10% 향상시키면 프로그램 전체의 속도가 거의 10% 향상된다."

Donald Knuth (1974)

무라토리의 역산

루프 밖 코드는 그대로이므로 줄어든 시간은 루프에서 줄어든 시간과 같습니다. "거의 10%"를 9% 이상으로 잡으면(무라토리의 보수적 가정):

Torig − Topt = Corig − Copt = 0.1 × Corig
(Torig − Topt) ÷ Torig ≥ 0.09
따라서 Corig ÷ Torig ≥ 0.09 ÷ 0.10 = 90%

T는 프로그램 전체 실행 시간, C는 그 루프의 실행 시간입니다(orig는 최적화 전, opt는 후). 즉 크누스의 말이 성립하려면 3%의 코드가 실행 시간의 90% 이상을 차지해야 합니다.

직접 계산해 보기

참고로 원문이 전하는 실측 비중 50%(8절)에 루프 10% 단축을 넣으면 전체는 5%만 줄어듭니다.

8

크누스가 인용한 1971년 데이터

90%는 어디에도 없었다

1974년 논문의 각주가 인용한 문헌은 두 편입니다. 크누스 본인의 『An Empirical Study of FORTRAN Programs』(1971)와 댄 잉걸스의 『The Execution Time Profile as a Programming Tool』(1971)입니다.

크누스는 1970년 여름 실제 프로그램을 모았습니다. 전산실 쓰레기통의 카드는 컴파일 에러투성이였고, 전산실 앞에서 묻는 방법도 포기했습니다. 결국 스탠퍼드 디스크의 '반보호' 파일을 스캔해 록히드 코드와 함께 440개 프로그램(천공 카드 250,000장)을 확보했습니다.

구문 유형440개 합계 (회)프로그램당 평균 (회)
배정문78,435178.2
조건문 (IF)27,94063.5
분기문 (GOTO)24,64056.0
루프문 (DO)10,56024.0

프로그램 하나가 아주 작았다는 뜻입니다. 1971년 논문에는 90%가 없고 이렇게만 적혀 있습니다.

"우리는 또한 프로그램의 4% 미만이 대개 실행 시간의 절반 이상(more than half, 즉 50% 이상)을 차지한다는 사실을 발견했다."

크누스, 1971 (원문 인용)

무라토리는 디지털본이 없는 잉걸스 논문의 심포지엄 프로시딩 원본을 이베이에서 구해 스캔했습니다. 잉걸스의 FORTRAN 계측 도구 FORTUNE의 출력을 보면 결과는 이렇습니다.

항목크누스 1974년 주장잉걸스 1971년 실측
소스 3%가 차지하는 실행 시간90%50%
가장 극단적인 프로그램의 1위 루틴 비중(해당 없음)66.7%, 나머지 33.3%는 여러 루틴에 분산

원문은 이를 평평한 프로파일(실행 시간이 한 곳에 몰리지 않고 여러 곳에 고르게 퍼진 상태)이라 부르고, 크누스의 가정이 자신이 인용한 데이터로도 뒷받침되지 않는다고 결론짓습니다.

9

1970년대 하드웨어의 비용 모델

종이 위 셈과 실제 기계

크누스는 명령어 가져오기 1회와 메모리 참조 1회를 각각 비용 1로 단순 합산했습니다. 원문은 1967년 출하된 IBM System/360 Model 91 매뉴얼을 근거로 실제 기계가 훨씬 복잡했다고 봅니다.

  • 루프 모드: 8더블워드(64바이트) 이하 루프를 감지하면 메인 메모리에서 명령어를 가져오지 않고 칩 안 버퍼에서 실행합니다.
  • 비순차 실행: 명령어를 준비된 순서대로 처리합니다. 토마술로 알고리즘을 처음 하드웨어로 구현했습니다.
  • 분기 버퍼: 분기 때 파이프라인이 멈추지 않도록 미리 가져옵니다.

그래서 원문은 예제 2a처럼 루프를 펼쳐 8더블워드를 넘기면 루프 모드가 풀려 오히려 느려졌을 수 있다고 봅니다.

관점내용

10

강연 뒤 질의응답

gingerBill과 나눈 세 가지 쟁점

Odin 언어를 만든 gingerBill이 무라토리와 대담했습니다.

  • GOTO와 break: 1974년 논문의 GOTO 예제는 오늘날 break, continue로 씁니다. 무라토리는 당시엔 이것이 표준이 아니었고, '루프 앤드 어 하프'(조건 검사 전 한 번 실행하는 구문)를 두고 경쟁 제안이 많았다고 답합니다.
  • ALGOL 배열 인덱스: ALGOL 60 배열은 1부터 시작하도록 고정된 것이 아니라 array A[-3:7];처럼 아무 정수 범위나, 실행 중 계산한 식으로도 경계를 정할 수 있었습니다. 데이크스트라는 뒤에 0부터 세는 반열린 구간 [0, N)을 주장했습니다.
  • 호어와 SSA: SSA(정적 단일 대입, 변수마다 값을 한 번만 대입하는 컴파일러 표현)를 호어가 공식 발명 15년 전에 이미 문서에 서술했다고 두 사람은 말합니다.

결론

유해한 추상화가 된 격언

무라토리는 새 교훈 하나를 강요하지 않겠다고 했습니다. 이 격언 자체가 1974년의 맥락, 하드웨어 제약, 수학적 세부를 지운 '유해한 추상화'였다는 이유입니다. 'GOTO는 유해하다'가 교조가 되었듯, 이 격언도 성능을 포기하는 방패가 됐다는 것입니다.

"추상화의 서로 다른 층위를 도입한다고 해서, 다른 층위를 완전히 무시해도 된다고 내가 암시했다면 깊은 죄책감을 느낍니다. 그것은 결코 사실이 아닙니다. ..."

데이크스트라, 크누스에게 보낸 서신 (원문 인용)

원문이 제시하는 2026년의 교훈은 세 가지입니다.

  1. 미시적 조기 튜닝은 여전히 해롭습니다. 구조가 정해지기 전에 코드를 꼬면 유지보수를 해칩니다.
  2. 그러나 아키텍처 수준의 조기 설계는 필수입니다. 메모리 배치, 캐시 친화적 자료구조, 데이터 흐름은 나중에 3%만 고쳐서 바로잡을 수 없습니다. 호어의 컴파일러가 그 예입니다.
  3. 슬로건 뒤에 숨지 말고 원전을 읽어야 합니다.
12

읽으며 걸린 곳

정리하면서 제가 찾은 것. 결론에는 영향이 크지 않습니다

8가지 보기
  • 원문은 세 사람이 "8년 터울로 태어나 8년 터울로 튜링상을 받았다"고 쓰지만, 원문 표대로면 출생은 4년 간격(1930, 1934, 1938년), 수상은 1972, 1974, 1980년입니다.
  • 컴파일 속도 그림은 2자에서 8자로 오른 것을 "400% 빨라졌다"고 씁니다. 4배는 300% 증가입니다.
  • 1971년 데이터가 섞여 있습니다. 크누스 1971년 논문은 "4% 미만이 절반 이상"이라고 하고, 원문은 잉걸스 실측을 "3%가 정확히 50%"라고 합니다. 도식은 440개 프로그램 계측을 잉걸스 쪽에 넣었지만, 본문에서 440개는 크누스의 수집 결과입니다.
  • 도식의 "프로그램 크기: 약 180줄"은 프로그램당 배정문 178.2개에서 온 것으로 보이며, 줄 수와는 다릅니다.
  • "9% 이상"이라는 기준은 크누스가 아니라 무라토리의 가정입니다. 위 계산기는 이 가정을 바꿔 볼 수 있게 했습니다.
  • 도입부는 이베이에서 "1971년 천공카드 계측 보고서"를 낙찰받았다고 하고, 8절은 "심포지엄 프로시딩 원본 서적"이라고 합니다.
  • 현대 캐시 지연 수치, 호어의 컴퓨터 가격 환산(약 17억 원), SSA "15년" 주장, Ngram 그래프(개념도)에는 출처가 붙어 있지 않습니다. 1974년 인용문들도 한국어 번역본만 실려 있습니다.
  • 예제 2a가 Model 91 루프 모드를 벗어나 느려졌을 것이라는 서술은 원문의 추정이며 측정값은 없습니다.
